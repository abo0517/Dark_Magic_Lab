# AGENTS.md — 복지메이트 백엔드 개발 지침

> 적용 범위: 2026 서울AI디지털배움터 청년 AI 해커톤의 Supabase 백엔드 작업. 이 문서는 Codex의 작업 규칙이며 실제 API 명세나 검증된 DB 스키마를 대체하지 않는다.

## 1. 문서 우선순위와 협업

- 저장소의 `CODEX.md`를 팀 공통 규칙으로, `개발계획.md`를 구현 목표 및 일정 기준으로 읽는다. 이 파일은 **백엔드 세부 규칙**을 보충한다.
- 두 문서 또는 실제 코드가 충돌하면 조용히 한쪽을 선택하지 않는다. 충돌 내용과 영향, 확인이 필요한 결정을 담당자에게 제시한다.
- 담당자: 백엔드 조계진·유예찬 / 프론트 강준 / 모델 안병욱·배준서.
- **자기 역할 폴더의 코드 파일만 수정한다.** 다른 역할의 코드를 직접 고치지 않고 필요한 인터페이스 변경 사항을 전달한다. 실제 폴더 이름은 저장소를 확인하고 판단한다.
- 작업 시작과 종료 시 현재 작업 폴더에 있는 모든 `역할-이름.md` 파일을 확인한다. 자신의 작업 진행은 백엔드 폴더의 `백엔드-조계진.md` 또는 `백엔드-유예찬.md` 등 담당자별 문서에 짧게 기록한다. 없는 파일을 임의로 다른 팀원 이름으로 만들지 않는다.
- 주석은 최소한으로 작성한다. 사실 확인이 필요하면 공식 문서·공공데이터포털 등을 조사하고 출처를 기록한다. 확인하지 않은 사항은 확정적으로 말하지 않는다.

## 2. 프로젝트 목표와 범위

- 프론트: React 18 + Vite 5, PWA.
- 백엔드: Supabase PostgreSQL, PostgREST, Edge Functions(Deno/TypeScript), 필요 시 Supabase Auth·Storage.
- 핵심 목표: (1) 하드코딩된 `mockCatalog`를 실제 공공 복지정책 데이터로 교체 (2) 목업 `analyze()`를 이미지/PDF 실제 분석 호출로 교체.
- 기본적으로 별도의 Spring Boot 서버를 만들지 않는다. 아키텍처 변경은 팀 승인 후 진행한다.
- GPU 없는 환경과 총 6시간 개발을 전제로 한다. 시작 후 **3시간 30분 이내 첫 배포**를 최우선 마일스톤으로 삼는다.
- 음성 안내는 프론트의 Web Speech API가 담당한다. 별도 서버 TTS는 구현하지 않는다.
- 기존 계획은 마이페이지·즐겨찾기·진행률·글자 크기 설정을 localStorage로 관리한다. 과거 논의의 소셜 로그인·회원별 체크리스트 DB 설계와 차이가 있으므로, 별도 확정 없이는 인증/회원 DB 기능을 추가하지 않는다.

## 3. API 경계 및 책임

### 3.1 `policies` 테이블 조회
- Supabase 자동 REST(PostgREST)로 정책 목록·상세를 제공한다.
- 공개 정책 데이터에 대해서만 필요한 `SELECT` 권한을 허용한다. 클라이언트의 INSERT/UPDATE/DELETE는 허용하지 않는다.
- 나이·지역·카테고리 필터는 DB 쿼리로 처리한다. 연령 기준의 경계값, 지역코드 매칭, NULL 처리 등은 실제 데이터에 맞춰 검증한다.
- 프론트가 직접 사용할 컬럼과 쿼리 계약을 문서화한다. 프론트 목업의 응답 필드를 무단으로 변경하지 않는다.

### 3.2 `sync-policies` Edge Function
- 중앙부처 및 지자체 정책 목록/상세 API를 호출하고 XML을 파싱·정규화하여 `policies`에 upsert한다.
- 팀 관리자만 실행할 수 있게 서버 측 인증·권한을 검증한다. 프론트에 동기화 권한이나 service_role 키를 노출하지 않는다.
- 개발계획의 수동 실행 **당일 1~2회**를 기본으로 한다. 자동 주기 실행은 요청 없이는 추가하지 않는다.
- 수집은 배치 처리(계획상 최대 100건 단위)하되 실제 API의 페이지 파라미터와 응답 제한을 확인한다.
- `serv_id`가 기관 간 중복될 가능성을 고려하여 `(source, serv_id)` 복합 유일키를 우선 검토한다. 원본 식별자 규칙을 확인한 후 마이그레이션한다.
- 중복 저장을 방지하고 재실행 가능한 멱등성(idempotency)을 보장한다. 개별 건 실패 시 전체 데이터를 지우지 않는다.
- 부분 실패·429·타임아웃·XML 오류를 구분해 기록한다. 호출량을 소모하는 무제한 재시도는 금지한다.

### 3.3 `analyze` Edge Function
- 이미지/PDF 안내문을 받아 모델 담당자와 확정한 JSON 응답을 프론트에 반환한다.
- 응답 형식은 `개발계획.md`의 "analyze 출력 데이터"를 따른다: `{ "easySummary", "programs"[19개 키], "hasPersonalInfo" }`. `source`는 프론트가 채우므로 래퍼나 필드를 추가하지 않는다.
- 모델은 확정되었다: Claude(`claude-sonnet-5-5`). `analyze`는 AI를 직접 부르지 않고 모델 서버 `POST {OCR_SERVER_URL}/analyze`(multipart 파일 필드 `file`, 헤더 `X-Shared-Secret`)로 전달만 한다. `OCR_SERVER_URL`과 `OCR_SHARED_SECRET`은 Edge Function secret에 둔다.
- OCR은 쓰지 않는다. 모델 서버(Python, 팀 컴퓨터)의 사용은 승인되었다. 서버가 돌려주는 오류 코드(`401 UNAUTHORIZED`, `413 TOO_LARGE`, `415 UNSUPPORTED`, `422 UNREADABLE`, `502 UPSTREAM_ERROR`, `504 TIMEOUT`)를 그대로 프론트에 전달하고, 서버에 닿지 않으면 502나 504로 구분한다.
- 모델 응답은 JSON 스키마 검증을 거친다. 불완전하거나 잘못된 출력은 명확한 오류로 처리한다.
- AI는 안내문에서 근거를 추출·정리한다. 대상 여부 최종 판정은 계획에 명시된 `judge()` 등 **결정론적 로직**에 맡긴다. 해당 함수가 프론트 또는 모델 폴더에 있으면 수정하지 않고 인터페이스를 협의한다.
- 원문에 없는 기한·대상·서류·제출처를 만들어내지 않는다. 판독 불가 시 합의된 `UNREADABLE` 상태를 반환한다.

## 4. 공공데이터 API 명세

### 4.1 중앙부처 복지서비스
- 제공기관: 한국사회보장정보원 / 공공데이터포털(data.go.kr)
- 기본 URL: `https://apis.data.go.kr/B554287/NationalWelfareInformationsV001`
- 목록: `/NationalWelfarelistV001`
- 상세: `/NationalWelfaredetailedV001`
- 계획상 일일 호출 제한: **100회**

### 4.2 지자체 복지서비스
- 제공기관: 한국사회보장정보원 / 공공데이터포털(data.go.kr)
- 기본 URL: `https://apis.data.go.kr/B554287/LocalGovernmentWelfareInformations`
- 목록: `/LcgvWelfarelist`
- 상세: `/LcgvWelfaredetailed`
- 계획상 일일 호출 제한: **1,000회**

### 4.3 공통 호출 규칙
- 일반 인증키는 코드, 문서, 브라우저 번들, 로그에 넣지 않는다. Supabase 서버 측 secret(`DATA_GO_KR_KEY`)에서 읽는다.
- API 요청 파라미터(인증키 파라미터명, 페이지 번호, 상세 식별자 등), 인코딩 방식, 응답 XML 구조는 **공공데이터포털 원문 명세와 실제 응답으로 확인**한다. 임의 추정하지 않는다.
- 일일 제한은 현재 계획에서 제시된 값이다. 운영 전 제공기관의 실제 쿼터·초기화 시각·오류 응답을 재확인한다.
- 호출량을 기록하고 목록 수집과 상세 수집의 예산을 별도로 계산한다. 100회 제한을 초과할 가능성이 있으면 요청을 중단하고 담당자에게 보고한다.
- 동일 요청 중복 호출을 줄이고, 이미 저장된 정책을 재사용한다. 불필요한 전체 재수집을 금지한다.
- XML 파서는 배열/단일 객체 형태 차이, 빈 태그, 문자 인코딩, 오류 응답을 안전하게 처리한다. 외부 엔티티 확장 등 위험한 XML 처리 기능은 비활성화한다.
- 외부 서비스 실패 시 기존 정상 DB 데이터를 보존한다.

## 5. 정책 테이블 초안

개발계획에 명시된 `policies` 필드:

| 영역 | 컬럼 |
|---|---|
| 기본 정보 | `serv_id`, `source`, `name`, `summary`, `category`, `ctpv`, `sgg` |
| 추출 정보 | `min_age`, `max_age`, `deadline`, `docs`, `office`, `eligibility` |
| 출처/갱신 | `detail_link`, `updated_at` |

- `source`는 `central` 또는 `local`로 제한한다.
- `docs`는 문서 목록 배열이다. PostgreSQL 타입(text[] 또는 jsonb)은 실제 응답 계약에 맞춰 확정한다.
- 추출된 조건은 불확실할 수 있다. 확인되지 않은 값은 임의 기본값으로 채우지 않고 NULL 또는 명시적인 미확인 상태로 보존한다.
- `updated_at`은 실제 출처 갱신일과 DB 동기화 시각을 혼동하지 않는다. 필요하면 별도 컬럼을 제안하되 무단 변경하지 않는다.
- 공개 정책 데이터만 저장한다. 주민등록번호·연락처·업로드 안내문 원본 등 개인정보를 정책 테이블에 저장하지 않는다.
- 실제 스키마를 먼저 확인한 후 SQL 마이그레이션을 작성한다. 기존 테이블을 무단 DROP/TRUNCATE하지 않는다.

## 6. Supabase 보안 및 비밀키

- `DATA_GO_KR_KEY`와 AI API 키(`ANTHROPIC_API_KEY`, AI는 Claude로 확정)는 Supabase Edge Function secrets로 관리한다. `analyze`는 모델 서버로 전달만 하므로 `OCR_SERVER_URL`, `OCR_SHARED_SECRET`도 secret으로 둔다. 키는 브라우저에 노출하지 않는다.
- `service_role` 등 관리자 권한 키는 브라우저에 노출하지 않는다. Supabase 공개 anon/publishable 키는 RLS가 올바르게 구성된 경우에만 프론트에서 사용한다.
- 공개 읽기 전용 정책과 동기화 관리자 권한을 분리한다.
- Edge Function의 인증 검증 설정을 배포 전에 확인한다. `sync-policies`는 단순히 비공개 URL이라는 이유로 안전하다고 가정하지 않는다.
- 파일 업로드 시 크기·MIME 타입·허용 형식·요청 빈도를 검증한다. 이미지/PDF는 가능한 한 메모리에서만 처리하고 Storage·DB·로그에 영구 저장하지 않는다.
- 외부 AI 제공업체로 파일이 전송되는 경우 프론트에서 사용자에게 알릴 수 있도록 필요한 문구를 전달한다. 개인정보 미저장과 외부 전송은 서로 다른 사실이다.
- 로그에 인증키, Authorization 헤더, 파일 내용, 개인 식별정보를 남기지 않는다.
- 사용자가 제공한 기존 인증키가 대화에 노출된 이력이 있으므로 재발급 여부를 담당자에게 확인한다.

## 7. API 응답 및 오류 처리

- 프론트와 확정한 기존 응답 형식을 우선한다. `analyze`의 성공 응답에 임의 래퍼를 추가하지 않는다.
- 오류는 일관된 HTTP 상태 코드와 안전한 JSON 메시지로 반환한다. 내부 스택 트레이스는 반환하지 않는다.
- 최소한 입력 오류(400), 인증/권한 오류(401/403), 요청 과다(429), 외부 API 장애(502/503), 내부 오류(500)를 구분한다.
- 외부 XML의 원본 오류 내용은 민감정보 여부를 확인한 뒤 로그에 필요한 범위만 남긴다.
- 네트워크 장애와 AI 판독 실패를 구분한다. `UNREADABLE`의 정확한 JSON 표현은 모델·프론트 팀과 합의한다.

## 9. 검증 기준

- `policies` 행 수와 외부 API의 실제 `totalCount`를 비교한다. 계획서의 중앙 461건·지자체 397건은 검증 목표 참고값이지 항상 보장되는 현재 수치가 아니다.
- `source`, 나이, 지역, 카테고리별 조회와 정책 상세를 확인한다.
- `sync-policies`를 재실행해도 중복 행이 생기지 않아야 한다.
- 중앙 100회·지자체 1,000회 예산을 넘지 않도록 실제 요청 수를 기록한다.
- 공개 사용자는 정책 SELECT만 가능하고 쓰기·관리자 동기화는 거부되어야 한다.
- `analyze`는 샘플 11장으로 검증한다. 기한·나이·서류·제출처 네 필드의 정확성을 평가하고 흐린 입력의 `UNREADABLE` 처리를 확인한다.
- 개발계획의 기준인 **11장 중 8장 이상 정확 추출**을 목표로 하되, 실제 시험 결과를 숨기지 않는다.
- 브라우저 네트워크 요청과 배포 번들에 비밀키가 없는지 확인한다.
- 실제 실행하지 않은 테스트는 통과했다고 보고하지 않는다.

## 10. Codex 실행 행동 규칙

- 작업 전 관련 코드·`CODEX.md`·`개발계획.md`·담당 폴더의 진행 문서를 읽는다.
- 요청 범위 내에서 최소한의 파일만 수정한다. 다른 담당자 폴더는 읽기만 한다.
- 외부 API 파라미터, 모델 API 계약, 실제 DB 구조를 추측해 구현하지 않는다. 모호하면 확인 질문 또는 명시적인 TODO로 남긴다.
- 스키마 변경·권한 완화·비밀키 변경·유료 API 대량 호출·프로덕션 데이터 삭제는 사전 승인 없이 수행하지 않는다.
- 변경 후 가능한 검증 명령을 실행하고 결과를 기록한다.
- 작업 종료 시 (1) 수정 파일 (2) 구현 기능 (3) 테스트 결과 (4) 남은 문제 (5) 프론트/모델 팀에 전달할 사항을 간결하게 보고한다.

## 11. 착수 전 확인할 미확정 사항

- AI 제공업체: Claude로 확정(모델 서버가 호출). `CODEX.md`의 OpenAI 문구는 정정되었다.
- 실제 프론트 `mockResult` 전체 스키마 및 `judge()`의 위치와 입력·출력 계약.
- 공공데이터 API의 필수 요청 파라미터, 실제 XML 응답, 인증키 인코딩 방식.
- 기존 회원/소셜 로그인/체크리스트 DB 기능을 해커톤 범위에 포함할지 여부.
- 실제 저장소 폴더 구조와 `policies` 테이블의 확정 SQL 타입·제약조건.
- 배포 URL, Edge Function 인증 방식, 운영 환경의 요청 제한 및 비용.
